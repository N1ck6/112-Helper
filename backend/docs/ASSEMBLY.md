# Как собрать комплекс из четырёх частей

> **Актуально:** комплекс собирается корневым `docker-compose.yml` репозитория
> (`docker compose --profile llm up -d --build`, см. [README](../../README.md)). Все части лежат в
> одном репозитории, браузер ходит через nginx `:8080`, телефония получает реплики собеседников
> прямо из ML (`/dialogue/turn`) и шлёт события в backend. Ниже — исходный замысел архитектуры.

Документ для всей команды: что кому отдавать, по каким адресам компоненты видят
друг друга и в каком порядке всё запускается.

---

## 1. Главное: это не один процесс, а четыре сервиса

ТЗ (п.4.4) требует собрать систему в разворачиваемый комплекс: отдельные контейнеры
для backend, frontend, Python/ML, PostgreSQL и SIP/VoIP, сетевое взаимодействие
между ними и **запуск всего комплекса одной процедурой**. То есть «монолит» здесь —
это не общий репозиторий и не один процесс, а один `docker compose up`, который
поднимает всё сразу.

Почему так, а не склеить в одно приложение:

* ML-часть тяжёлая (модели, torch) — её нельзя тащить в процесс, который должен
  отвечать за 2 секунды;
* SIP/VoIP живёт со своими портами и протоколами, у него своя жизнь;
* frontend — статика, её раздаёт nginx;
* при падении одного компонента остальные продолжают работать (п.4.5 ТЗ).

```
                    ┌──────────────┐
   браузер ────────▶│   frontend   │  :5173
                    └──────┬───────┘
                           │ REST + WebSocket
                    ┌──────▼───────┐        ┌──────────────┐
                    │   backend    │◀──────▶│  PostgreSQL  │
                    │     :8000    │        └──────────────┘
                    └───┬──────┬───┘
              HTTP JSON │      │ HTTP JSON + вебхук
                 ┌──────▼──┐ ┌─▼────────┐
                 │   ML    │ │ SIP/VoIP │
                 │  :8100  │ │  :8200   │
                 └─────────┘ └──────────┘
```

Backend — центр: он хранит состояние и вызывает остальных. ML и телефония между
собой не общаются, только через backend. Это сознательно: так у учебной сессии
один владелец и один источник правды.

## 2. Запуск

Файл сборки — корневой `docker-compose.yml` репозитория.

```bash
# весь комплекс с локальной LLM (Ollama + qwen3:4b-instruct)
docker compose --profile llm up -d --build

# только backend + база для разработки backend (папка backend/)
docker compose up -d postgres
```

В полном стенде backend работает с настоящими ML и телефонией; если ML не умеет метод или
недоступен, его выполняют правила backend (`HybridMLClient`), занятие не останавливается.

Проверка, что комплекс собрался:

```bash
python scripts/check_stack.py            # или: python scripts/check_stack.py --full
```

## 3. Что должен отдать каждый участник

| Участник | Что нужно от него | Куда это подставляется |
|---|---|---|
| Frontend | `Dockerfile`, который собирает статику и раздаёт её на порту 80 | сервис `frontend` |
| Python/ML | `Dockerfile` + HTTP-сервис на порту 8100 с методами из `INTEGRATION.md` §1 | сервис `ml` |
| Телефония | `Dockerfile` + сервис на 8200 (HTTP) и 5060/udp (SIP) | сервис `sip` |
| Backend | этот репозиторий | сервис `api` |

Адреса внутри сети комплекса (по именам сервисов, не по localhost):

| Откуда | Куда | Адрес |
|---|---|---|
| backend → ML | генерация, оценка, аналитика | `http://ml:8100` |
| backend → телефония | инициировать вызов, состояние | `http://sip:8200` |
| ML → backend | классификатор, материалы | `http://api:8000/api/v1` |
| телефония → backend | вебхук событий вызова | `http://api:8000/api/v1/telephony/events` |
| браузер → backend | REST и WebSocket | `http://localhost:8000` |

**Частая ошибка:** внутри контейнера `localhost` — это он сам. Обращаться к соседу
надо по имени сервиса (`http://ml:8100`), а `localhost` остаётся только для
браузера пользователя.

## 4. Контракты: что зафиксировано и менять нельзя без общего согласия

Все контракты описаны в [`INTEGRATION.md`](INTEGRATION.md), живая версия —
`http://localhost:8000/docs` и `http://localhost:8000/openapi.json`.

**Frontend ↔ backend.** Схемы запросов и ответов генерируются из кода: берите
типы из `openapi.json`, руками не переписывайте. Правила: форма карточки строится
по `GET /card-templates` и `/card-templates/field-groups`, видимость кнопок — по
массиву `permissions` из `GET /auth/me`, мониторинг занятия — по WebSocket
`/ws/lessons/{id}`.

**Backend → ML.** Семь методов (генерация, коррекция, оценка, грамматика,
аналитика, рекомендации, индексация материалов) плюс `/health`. Формат запроса и
ответа — в `INTEGRATION.md` §1. Эталон формата ответа — наша заглушка
`app/integrations/ml_client.py`: если ML отвечает так же, переключение делается
одной переменной `ML_USE_STUB=false`.

**ML → backend.** Классификатор происшествий: `POST /incidents/import` (результат
разбора таблицы) и чтение `GET /incidents/types`, `/incidents/{код}/features`.

**Телефония ↔ backend.** Backend просит создать вызов, телефония присылает события
(`ringing`, `answered`, `ended`, …) на вебхук с заголовком `X-Telephony-Token`.
Путь к аудиозаписи backend привязывает к карточке сам.

## 5. Порядок сборки: что делать в каком порядке

1. **Сейчас (пока части не готовы).** Все работают против backend с заглушками.
   Frontend разрабатывает по `openapi.json`, ML сверяет формат ответа с заглушкой,
   телефония шлёт события вебхуком руками (`curl`).
2. **Первая стыковка.** Поднять `--profile ml`, поставить `ML_USE_STUB=false` и
   провести одно занятие. Смотреть в `GET /admin/logs` — там видны ошибки формата.
3. **Вторая стыковка.** Поднять `--profile telephony`, `TELEPHONY_USE_STUB=false`,
   проверить, что аудиозапись привязалась к карточке.
4. **Полная сборка.** `--profile full`, прогнать сквозной сценарий целиком:
   звонок → карточка → действия → оценка → отчёт.
5. **Перед защитой.** Прогнать `scripts/check_stack.py --full` и нагрузочный
   сценарий (`docs/PERFORMANCE.md`).

## 6. Что уже сделано с нашей стороны для стыковки

* Внешние модули спрятаны за интерфейсом (`Protocol`) и заменяются заглушкой —
  переключение без правки кода, только `.env`.
* Если ML недоступен, работа обучающегося **не теряется**: оценка откладывается,
  задача уходит в очередь `outbox_messages` и повторяется с задержкой.
* `GET /health/ready` показывает состояние всех компонентов комплекса — по нему
  удобно понимать, кто из соседей не поднялся.
* Превышение норматива задержки VoIP (150 мс) пишется в системный журнал
  администратора, а не теряется.
* CORS настроен на адрес frontend'а, каждый ответ несёт `X-Request-ID` — по нему
  ошибка ищется в журналах всех компонентов.
