# Нагрузочное тестирование: методика и результаты

Документ подтверждает требования п.2.8 ТЗ фактическими замерами, а не расчётами.

---

## 1. Что требует ТЗ

| Требование | Значение |
|---|---|
| Отклик интерфейса под нагрузкой | ≤ 2 секунды при 100 пользователях |
| Одновременные учебные сессии | не менее 20 |
| Операции записи в БД | не менее 100 в секунду |
| Восстановление сессии после сбоя сети | до 30 секунд |
| Формирование аналитического отчёта | ≤ 30 секунд |

---

## 2. Как измеряется

Чтение страниц такой нагрузки не создаёт, поэтому сценарий гоняет реальный цикл
работы диспетчера ДДС: получить карточку → «Принята» → «Начало реагирования» →
«Прибытие» → «Проведение работ» → «Работы завершены». Последний статус закрывает
карточку, запускает автоматическую оценку и выдаёт следующую карточку — то есть
работает тот же путь, что и на занятии.

```powershell
python -m scripts.load_setup --students 100 --cards 900   # 100 учётных записей, занятие, запас карточек
uvicorn app.main:app --workers 2                          # рабочий процесс(ы) API
locust -f locustfile.py --headless -u 100 -r 10 -t 90s --host http://127.0.0.1:8000
```

`scripts/load_setup.py` создаёт группу «НАГР-01», сто обучающихся, запущенное занятие
в режиме «действия с карточками» и нужное число карточек, а параметры пишет в
`var/load_fixture.json` — оттуда их берёт `locustfile.py`.

Число операций записи считается независимо от Locust: количеством строк, реально
появившихся в таблицах `response_statuses`, `student_actions`, `card_attempts`,
`evaluations`, `error_records`, `card_answers`, `audit_logs`, `system_logs` за время
прогона. Это честнее, чем считать HTTP-запросы: один статус реагирования порождает
несколько записей.

## 3. Результаты прогона

**Стенд:** 2 vCPU, 8 ГБ RAM, Linux; PostgreSQL 16, генератор нагрузки и два рабочих
процесса uvicorn — на той же машине (то есть условия заведомо хуже боевых, где
СУБД и генератор нагрузки разнесены).

**Параметры:** 100 виртуальных пользователей, разгон 10 польз./с, длительность 90 с,
ML и телефония на заглушках.

| Показатель | Норматив ТЗ | Факт |
|---|---|---|
| Запросов всего | — | 8378 |
| Ошибок | — | **0** |
| Медиана отклика | — | 580 мс |
| 95-й процентиль отклика | ≤ 2000 мс | **1700 мс** |
| Пропускная способность API | — | 93 запроса/с |
| Операций записи в БД | ≥ 100 в секунду | **203 в секунду** |
| Одновременных учебных сессий | ≥ 20 | **100** |
| Карточек полностью отработано | — | 1237 |

Отклик по операциям (95-й процентиль):

| Операция | Медиана | 95% |
|---|---|---|
| `GET /auth/me` | 330 мс | 690 мс |
| `POST /training/lessons/{id}/next-card` | 480 мс | 1000 мс |
| `POST /training/attempts/{id}/response-status` | 610 мс | 1500 мс |
| `GET /evaluations/my` | 520 мс | 940 мс |

**Про вход в систему.** `POST /auth/login` занимает несколько секунд при разгоне,
и это ожидаемо: пароль проверяется bcrypt'ом, который намеренно дорог по процессору
(вход — разовая операция, а не рабочая). Стоимость вынесена в параметр
`PASSWORD_HASH_ROUNDS` (по умолчанию 12). Норматив отклика ≤ 2 с относится к рабочим
операциям, поэтому в таблице выше они приведены отдельно.

## 4. Что было исправлено по результатам первого прогона

Первый прогон дал 95-й процентиль 2300 мс и 88 ошибок. Разбор показал две причины,
обе устранены:

1. **Загрузка всех участников занятия на каждое действие.** Связь
   `Lesson.participants` объявлена `lazy="selectin"`, поэтому любое чтение занятия
   тянуло сотню строк участников. Добавлен `LessonRepository.get_light()` с
   `noload()`, и горячие пути (выдача карточки, простановка статуса, сдача,
   восстановление сессии) используют его.
2. **Поиск участника перебором коллекции.** `_participant()` искал участника в
   загруженной коллекции; теперь это точечный запрос по индексу
   `(lesson_id, student_id)`.

После правок: 0 ошибок, 95-й процентиль 1700 мс, запись 203 операции/с.

## 5. Куда расти дальше

Замер сделан на двух ядрах и одном экземпляре сервиса. Если понадобится больший
запас:

* **Рабочие процессы.** `uvicorn --workers N` по числу ядер: сервис не хранит
  состояние занятия в памяти процесса, состояние живёт в PostgreSQL.
* **Горизонтальное масштабирование.** Единственное место, привязанное к процессу, —
  WebSocket-хаб мониторинга (`app/services/realtime.py`): при работе в кластере его
  заменяют на Redis Pub/Sub. Это отмечено в коде.
* **Пул соединений.** `DB_POOL_SIZE` / `DB_MAX_OVERFLOW`; при нескольких экземплярах
  сервиса разумно поставить перед PostgreSQL pgbouncer.
* **Оценка.** Сейчас оценка считается синхронно при закрытии карточки. При включении
  реального ML-сервиса её стоит переводить в очередь: механизм уже есть —
  `outbox_messages` с экспоненциальным повтором.

## 6. Остальные нормативы п.2.8

* **Восстановление сессии до 30 секунд** — `POST /api/v1/training/resume`,
  проверяется автотестом в `tests/test_training_flow.py` (поле `within_grace_period`).
* **Формирование отчёта ≤ 30 секунд** — время пишется в `generation_ms` каждого
  отчёта; проверяется автотестом в `tests/test_attestation_and_formats.py`.
* **Медленные запросы** видны в метриках Prometheus: счётчик
  `dds112_http_requests_slow_total` (запросы дольше 2 секунд) — `GET /metrics`.
