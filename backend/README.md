# Backend тренажёра оператора ДДС-112

Серверная часть учебного программного обеспечения для подготовки операторов дежурно-диспетчерских
служб города Москвы (эмулятор АРМ-112, ГБУ «Система 112»).

Реализует **раздел 2 «Backend»** файла распределения задач: архитектура и REST API, схема PostgreSQL,
пользователи и RBAC, учебный процесс, карточки АРМ-112, отчётность, логирование и аудит,
производительность и интеграции.

Стек: **Python 3.11 · FastAPI · SQLAlchemy 2.0 (async) · PostgreSQL 16 · Alembic · pytest**.

---

## 1. Быстрый старт

```bash
# 1. Виртуальное окружение
python -m venv .venv
.venv\Scripts\activate            # Windows
# source .venv/bin/activate       # Linux / macOS

# 2. Зависимости
pip install -r requirements-dev.txt

# 3. Настройки
copy .env.example .env            # Windows;  cp .env.example .env — Linux/macOS

# 4. База данных (если нет локального PostgreSQL — поднять контейнером)
docker compose up -d postgres

# 5. Схема БД
alembic upgrade head

# 6. Стартовые данные (роли, пользователи, классификатор, сценарии)
python -m scripts.seed

# 7. Запуск
uvicorn app.main:app --reload
```

Документация API: <http://localhost:8000/docs> · Метрики: <http://localhost:8000/metrics>

Учебные учётные записи после `scripts.seed` при запуске backend **без Docker** (пароли по умолчанию;
в стенде из корня пароли свои — `ADMIN_PASSWORD`, `TEACHER_PASSWORD`, `STUDENT_PASSWORD` в корневом `.env`):

| Логин      | Пароль         | Роль                  |
|------------|----------------|-----------------------|
| `admin`    | `Admin#2026`   | Администратор системы |
| `teacher`  | `Teacher#2026` | Преподаватель         |
| `student`  | `Student#2026` | Обучающийся           |
| `student2` | `Student#2026` | Обучающийся           |

Вариант «всё в контейнерах»: `docker compose up --build` — поднимет PostgreSQL, применит миграции
и запустит API на порту 8000.

**Весь комплекс команды** (backend + frontend + ML + телефония) — из корня репозитория
([README](../README.md)):

```bash
docker compose up -d --build
python backend/scripts/check_stack.py --full      # проверка, что части видят друг друга
```

В полном стенде backend работает с настоящими ML-сервисом и телефонией (`ML_USE_STUB=false`,
`TELEPHONY_USE_STUB=false`); чего ML не умеет — считают правила backend (`HybridMLClient`).

## 2. Архитектура

Слоистая схема: каждый слой знает только о слое ниже.

```
HTTP / WebSocket
      │
   app/api/          — маршруты, схемы запроса-ответа, проверка прав (RBAC)
      │
   app/services/     — бизнес-логика: занятия, карточки, оценки, отчёты, аудит
      │
   app/repositories/ — доступ к данным, SQL-запросы
      │
   app/models/       — модели SQLAlchemy (41 таблица)
      │
   PostgreSQL
                     ↘ app/integrations/ — ML-сервис, телефония, метрики, outbox-буфер
```

Правила, которые держат проект расширяемым:

| Правило | Зачем |
|---|---|
| Эндпоинт не содержит логики, сервис не знает о HTTP | логику можно переиспользовать в воркерах, CLI, WebSocket |
| Запросы к БД только в репозиториях | замена выборки, кеш, шардирование — в одном месте |
| Состояние занятия — в PostgreSQL, не в памяти процесса | можно запускать несколько экземпляров API (горизонтальное масштабирование) |
| Внешние модули — за интерфейсом (`Protocol`) + заглушка | backend работает и разрабатывается без готовых ML и SIP |
| Права — атомарные строки `объект:действие`, роль = набор прав | новые роли без правки кода |
| Структура карточки — в данных (шаблон), а не в колонках БД | заказчик меняет состав полей АРМ-112 без миграций |

### Сквозной поток одной карточки

```
Преподаватель: POST /lessons → POST /lessons/{id}/start
Обучающийся:   POST /training/lessons/{id}/join
               POST /training/lessons/{id}/next-card   → карточка + дедлайн (норматив 30 с)
                    ↳ backend просит модуль телефонии имитировать входящий вызов
               POST /training/attempts/{id}/actions    → каждое действие с отметкой времени
               PUT  /training/attempts/{id}/draft      → промежуточное сохранение
               POST /training/attempts/{id}/submit
                    ↳ backend считает длительность и отклонение от норматива
                    ↳ отдаёт ML-сервису эталон + действия + текст → получает оценку и ошибки
                    ↳ сохраняет оценку, замечания, историю → выдаёт следующую карточку
Преподаватель: GET  /lessons/{id}/monitor  (или WebSocket /ws/lessons/{id})
               POST /evaluations/{id}/override   → правка оценки с записью в аудит
               POST /reports                     → отчёт о занятии (JSON/CSV/PDF)
```

### Режим «действия с карточками»: статусы реагирования

Этот режим воспроизводит реальную работу диспетчера ДДС на АРМ-112 по памятке
«Работа на АРМ-112» (ГБУ «Система 112», 2025) — первичному источнику данных из п.11 ТЗ.
Обучающийся получает уже готовую карточку и отражает ход реагирования своей службы.

```
Добавлена ─→ Получена службой          (проставляет система при выдаче карточки)
                 ├─→ Принята ──→ Начало реагирования → Прибытие → Проведение работ
                 │                 ├─→ Работы завершены          (закрывает карточку)
                 │                 └─→ Отказ от выполнения работ (закрывает карточку)
                 └─→ Не принята ──→ только в «Принята»
```

Правила, зашитые в backend:

* **Норматив 30 секунд** — первичный статус «Принята»/«Не принята» должен быть проставлен
  в течение 30 секунд после направления карточки в службу (ПП РФ № 1931). Просрочка
  фиксируется в `is_response_late`, а карточка уходит в состояние «Не оповещено».
  Это срок именно на первый статус: на полную отработку карточки даётся отдельное
  время (`CARD_ACTION_WORK_LIMIT_SECONDS`), иначе цепочка статусов в него не укладывается.
* **Строгая последовательность** — перепрыгнуть через приём карточки нельзя,
  «Не принята» переводится только в «Принята».
* **Обязательный комментарий** для «Не принята» и «Отказа от выполнения работ»:
  без указания причины отдел контроля считает это нарушением.
* **Закрытие карточки** — «Работы завершены» и «Отказ» делают её нередактируемой
  и сразу запускают оценку.

* **Список оповещения (ЕКП).** Службы, получившие карточку, формируются автоматически
  по единому классификатору происшествий и признакам карточки (`app/core/arm112.py`,
  таблица `notify_services` у категории). Службу можно добавить, но не удалить — как в
  ПОВ-112. Обучающийся работает от имени профильной службы своей карточки; попытка
  проставить статус за службу вне списка отклоняется.
* **Особенности служб.** Служба 103 не проставляет «Не принята» и «Отказ от выполнения
  работ» — вместо них «Работы завершены» с комментарием. Отказ профильной службы от
  реагирования — отдельное нарушение (`primary_service_refused`).
* **Статусы карточки.** «Не оповещено» (нет первичного статуса), «Отказ», «Не завершено»
  (работы не закрыты за 48 часов — проверяет регламентная задача), «Завершена».

Эндпоинты: `GET /training/attempts/{id}/response-options` (что доступно сейчас,
сколько секунд осталось, список оповещения и подсказки по формулировкам) и
`POST /training/attempts/{id}/response-status`.

Оценка в этом режиме считается по статусам, а не по заполнению полей:
`0.35·тайминг + 0.30·правильность решения + 0.25·регламент + 0.10·формулировки`.
Коды замечаний соответствуют нарушениям из памятки: `primary_status_missing`,
`primary_status_late`, `wrong_primary_status`, `comment_missing`, `comment_incomplete`,
`progress_statuses_missing`, `final_status_mismatch`.

### Состав карточки происшествия

Поля карточки живут в данных (`CardTemplate.fields_schema`), а не в колонках БД:
состав задаёт заказчик. Эталонный набор взят из раздела «Состав карточки происшествия»
памятки и лежит в `app/core/arm112.py` — 34 поля в восьми блоках:

| Блок | Поля |
|---|---|
| Информация о карточке | номер в системе-112, дата сохранения, кто зарегистрировал, номер оператора и АРМ |
| Телефоны | АОН, предоставленный, телефон на место |
| Заявитель | ФИО, статус (участник / очевидец / родственник…) |
| Адрес | формализованный по базе Яндекс (округ, район, улица, дом, корпус, квартира, подъезд, этаж, код), описательный адрес, координаты |
| Что случилось | признаки опросной карты, класс происшествия, класс ВИС |
| Признаки и метки | пострадавшие, количество, отказ от скорой, заблокированные, метка ЧС/ЧП |
| Описание | неформализованная информация |
| Отработка и оповещение | строки отработки, список оповещения, сообщение заявителю |

Frontend получает блоки через `GET /api/v1/card-templates/field-groups`, а поля —
через `GET /api/v1/card-templates`.

### Аттестация и переподготовка

Занятие создаётся с `purpose`: `training` (учебное), `attestation` (аттестация),
`refresher` (периодическая переподготовка). Для аттестации указывается `passing_score`
(по умолчанию `ATTESTATION_PASS_SCORE`). При завершении занятия backend считает
средний балл каждого участника и выставляет решение о зачёте (`final_score`,
`is_passed`), пишет итоги в аудит и позволяет напечатать протокол:
`POST /reports {"type": "attestation", "format": "pdf", "lesson_id": "…"}`.

Сертификат выдаётся только при пройденной аттестации: без зачёта
`POST /certificates` вернёт `attestation_not_passed`.

### Единый классификатор происшествий (ЕКП)

Классификатор заказчика — таблица, где комбинация признаков даёт итоговый тип
происшествия и набор служб:

```
«ДТП пострадавшие» + «Наезд на препятствие» + «Светофор»
      → «ДТП с пострадавшими — наезд на светофор», главная служба — полиция
```

Таблица разбирается **один раз** при импорте, дальше приложение работает с
нормализованными записями — исходный файл не является зависимостью времени
выполнения. Ведомственные классификаторы (МЧС, МВД, СМП…) хранятся в
`agency_classifiers`, исходная строка — в `raw` для сверки.

| Операция | Эндпоинт |
|---|---|
| Категории классификатора | `GET /incidents/categories` |
| Типы происшествий (фильтры, поиск) | `GET /incidents/types` |
| Тип по коду или идентификатору | `GET /incidents/{code}` |
| Признаки типа | `GET /incidents/{code}/features` |
| Импорт нормализованных записей | `POST /incidents/import` |
| Импорт самой таблицы | `POST /incidents/import/xlsx` |

Если у карточки указан `incident_type_code`, список оповещения берётся из
классификатора заказчика, а службы категории добавляются следом (удалить службу
из списка нельзя — правило памятки).

### Обмен данными с внешними системами

| Операция | Эндпоинт |
|---|---|
| Выгрузка карточек (JSON / XML) | `GET /cards/export?format=xml&with_expected=true` |
| Пакетный импорт карточек | `POST /cards/import` (файл .xml или .json) |
| Пакетная загрузка материалов | `POST /materials/bulk` (архив .zip) |
| Импорт классификатора происшествий | `POST /incidents/import` (JSON) или `/import/xlsx` |
| Синхронизация учётных записей с каталогом организации | `POST /users/sync-directory` |
| Резервная копия базы | `POST /admin/backups` |

Коды полей в файлах обмена — те же, что в составе карточки АРМ-112, поэтому словарь
соответствий не нужен. Учётные записи из каталога помечаются `auth_source=directory`:
их пароль тренажёр не хранит, проверку выполняет каталог.

## 4. Работа без готовых модулей команды

При `ML_USE_STUB=true` и `TELEPHONY_USE_STUB=true` backend полностью автономен:

* **ML-заглушка** (`StubMLClient`) — не «случайные числа», а прозрачные правила: сравнение с эталоном
  по полям, проверка последовательности действий (LCS), контроль норматива времени, проверка
  формулировок. Итог: `0.40·точность + 0.25·регламент + 0.20·тайминг + 0.15·грамматика`.
  Её результаты пригодятся как контрольные при сверке с нейросетью.
* **Заглушка телефонии** — «вызов» создаётся логически, занятие идёт в текстовом режиме
  (ТЗ это допускает).

Переключение на реальные сервисы — только правка `.env`, код не меняется.
Контракты описаны в [`docs/INTEGRATION.md`](docs/INTEGRATION.md).

```bash
python scripts/setup_local.py          # первая установка одной командой (БД, .env, миграции, тесты)
uvicorn app.main:app --reload          # запуск в разработке
alembic upgrade head                   # применить миграции
alembic revision --autogenerate -m "…" # новая миграция после правки моделей
alembic downgrade -1                   # откатить последнюю
python -m scripts.seed                 # стартовые данные (идемпотентно)
pytest -q                              # тесты (нужна база из TEST_DATABASE_URL)
ruff check . && ruff check --fix .     # линтер

python -m scripts.load_setup --students 100 --cards 900   # стенд нагрузочного тестирования
locust -f locustfile.py --headless -u 100 -r 10 -t 90s --host http://127.0.0.1:8000
```

## 7. Ограничения текущей версии (честно)

* **Восстановление из резервной копии** не автоматизировано: копию снимает сервис
  (`POST /admin/backups`, `pg_dump`), но откат базы делает администратор вручную —
  команда отдаётся в поле `restore_command`. Кнопка «восстановить базу» в веб-интерфейсе
  слишком опасна. Автоматическое копирование по расписанию включается параметром
  `BACKUP_ENABLED` (по умолчанию выключено: процессу нужен доступ к `pg_dump`).
* **Запуск/остановка сервисов** — команда фиксируется в `service_states` и аудите, физически
  контейнерами управляет оркестратор (зона участника 4). Доступ к Docker-сокету из API недопустим.
* **Каталог доступа** работает на заглушке (`StubDirectoryClient`) пока не задан
  `DIRECTORY_URL`: она отдаёт две учебные записи и всегда отклоняет пароль — чтобы
  заглушка не стала обходом контроля доступа.
* **WebSocket-подписки** живут в памяти процесса. При запуске нескольких экземпляров API
  нужен брокер — менять только `app/services/realtime.py`.
* **Формат обезличенной выгрузки системы-112** реализован по составу полей из памятки
  (`app/integrations/exchange.py`). Когда заказчик даст свой формат, потребуется адаптер
  к нему — менять только этот модуль.
* Пароли в `scripts/seed.py` — учебные, для промышленного контура завести учётные записи
  через API либо синхронизацией с каталогом организации.

## 8. Следующие шаги для команды

1. **Frontend** — брать контракт из `/openapi.json`; поля карточки не «хардкодить», а строить форму
   по `GET /api/v1/card-templates` и `/card-templates/field-groups`.
2. **Python/ML** — реализовать 7 методов из `docs/INTEGRATION.md`; `StubMLClient` служит эталоном
   формата ответа. Классификатор происшествий загружать через `POST /api/v1/incidents/import`.
3. **Телефония/Docker** — присылать события на `POST /api/v1/telephony/events` с заголовком
   `X-Telephony-Token`; путь к аудиозаписи backend сам привяжет к карточке.
4. **Сборка** — корневой `docker-compose.yml` (весь комплекс одной командой).
