# ML — ИИ-сервис тренажёра ДДС-112

Python-сервис (FastAPI) для «интеллектуальной» части тренажёра: понимает текст о происшествии,
классифицирует его по официальному классификатору заказчика, генерирует учебные сценарии,
оценивает ответы, проверяет грамотность, даёт рекомендации и отвечает голосом собеседников
в учебных звонках. Работает локально, без интернета: LLM — Qwen в Ollama на том же сервере.

> **Главный принцип.** Тип происшествия и службы берутся из официального классификатора
> `Klassifikator.xlsx`, а не придумываются нейросетью. LLM пишет только текст (рассказ заявителя,
> рекомендации, разбор грамотности) и всегда имеет запасной вариант по правилам.

## Что умеет

| Возможность | Как | Где используется |
|---|---|---|
| Классификация описания происшествия | сопоставление с 1283 типами из 24 категорий классификатора (`matcher.py`) | поиск «Что случилось?» в АРМ, генерация сценариев |
| Анализ текста: факты, неизвестные, краткое содержание | LLM (`llm_processor.py`) | `/analyze`, `/classify_with_llm` |
| Генерация учебного сценария | тип из классификатора + вопросы, эталонные действия, критерии оценки (`scenario_generator.py`) | кабинет преподавателя «Сценарии», установка стенда |
| Эталон карточки АРМ-112 для сценария | тип ЕКП, реальный адрес Москвы, ФИО и АОН заявителя, пострадавшие, рассказ заявителя от первого лица (LLM, без неё — шаблон) | карточки занятий, оценка обучающегося |
| Оценка свободного текстового ответа | критерии сценария, пропущенные действия, ошибки (`evaluator.py`) | `/evaluate`, `/api/v1/evaluate/attempt` |
| Проверка грамотности | LLM находит ошибки в тексте карточки и предлагает исправление | «Принудительная проверка грамматики» в backend |
| Рекомендации по ошибкам | LLM по статистике ошибок обучающегося или группы | «Оценка ИИ» → «Рекомендации ИИ группе» |
| Реплики собеседников в звонках | правила по памятке АРМ-112 или LLM (`integration/dialogue.py`) | телефония, звонок «В браузере» |

## Как устроен

```text
ml/
├── api.py                  FastAPI: собственные методы ML + подключение integration/
├── classifier.py           чтение Klassifikator.xlsx: категории, группы, признаки, типы, главная служба
├── matcher.py              сопоставление текста с типами классификатора (признаки, синонимы, веса)
├── llm_processor.py        Qwen через Ollama: факты, неизвестные, краткое содержание
├── scenario_generator.py   учебный сценарий по типу происшествия и уровню сложности
├── evaluator.py            оценка ответа оператора по критериям сценария
├── integration/            контракты для других частей комплекса (ТЗ, §6)
│   ├── routes.py           маршруты /dialogue/turn, /incident-types, /api/v1/...
│   ├── dialogue.py         реплики собеседников: правила и LLM
│   ├── backend_contract.py генерация и оценка в формате backend
│   └── llm.py              JSON-запросы к Ollama: грамотность, рекомендации
├── data/
│   ├── raw/                Klassifikator.xlsx, tickets_32.txt — исходные данные заказчика
│   ├── processed/          результаты разбора обращений и классификации
│   └── dialogue_scenarios/ сценарии голосовых вызовов 112 (номера 700/701)
├── main.py                 ручная проверка классификатора, генерации и оценки
├── parse_tickets.py        разбор обращений из tickets_32.txt
└── analize_matches.py      анализ качества классификации
```

```text
текст обращения ──> matcher (классификатор) ──> тип, категория, главная служба
                         │
                         ├──> scenario_generator ──> сценарий: вопросы, действия, критерии
                         │                               └──> backend_contract ──> эталон карточки + рассказ (LLM)
                         └──> llm_processor (Qwen) ──> факты, неизвестные, краткое содержание
```

## Запуск

**В составе стенда** (основной способ) — из корня репозитория:

```bash
docker compose --profile llm up -d --build
```

- API ML на хосте: http://localhost:8100/docs, внутри сети Docker — `http://ml:8000`.
- Профиль `llm` поднимает Ollama и при первом старте скачивает `qwen3:4b-instruct` (~2.5 ГБ).
- Без профиля сервис работает без LLM: классификатор, генерация и правила есть, а грамотность,
  рекомендации и рассказы заявителей отдаются правилами и шаблонами (методы LLM отвечают 501,
  backend выполняет их своими правилами).

**Отдельно, для разработки** (Python 3.12, Ollama установлена на машине):

```bash
python -m venv .venv
```

```bash
.venv\Scripts\activate
```

```bash
pip install -r requirements.txt
```

```bash
ollama pull qwen3:4b-instruct
```

```bash
set OLLAMA_URL=http://127.0.0.1:11434
```

```bash
uvicorn api:app --reload --host 127.0.0.1 --port 8000
```

Документация API — http://127.0.0.1:8000/docs. В Linux/macOS: `source .venv/bin/activate` и `export OLLAMA_URL=…`.

## API

### Собственные методы ML

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/health` | состояние: загружен ли классификатор, сколько типов и категорий, модель LLM |
| POST | `/classify` | `{"text"}` → тип, категория, номер, главная служба, уверенность, 3 альтернативы |
| POST | `/analyze` | `{"text"}` → факты, неизвестные, краткое содержание (LLM) |
| POST | `/classify_with_llm` | анализ LLM + классификация одним запросом |
| POST | `/generate_scenario` | `{"difficulty": "easy|medium|hard", "incident_number"}` → учебный сценарий |
| POST | `/evaluate` | `{"scenario", "operator_answer"}` → балл, выполненные и пропущенные действия, ошибки |

Пример классификации:

```json
POST /classify  {"text": "Во дворе горит машина, водитель внутри"}
→ {"status": "confident", "incident_type": "пожар: машина", "category": "Пожары и задымления",
   "incident_number": "1020201", "main_service": "MCHS", "score": 50.73, "alternatives": [...]}
```

### Контракты для других частей (`integration/`)

| Метод | Путь | Кто вызывает | Что делает |
|---|---|---|---|
| POST | `/dialogue/turn` | телефония, backend | реплика собеседника по истории разговора (контракт `telephony/API.md` §3) |
| GET | `/dialogue/health` | мониторинг | движок реплик (`rules` / `llm:<модель>`) и сценарии 112 |
| GET | `/incident-types?q=&limit=` | АРМ через nginx (`/ml/incident-types`) | поиск типов по частям слов: «задым электрощит» |
| POST | `/api/v1/generate/scenarios` | backend | сценарии с эталоном карточки АРМ-112 |
| POST | `/api/v1/evaluate/attempt` | backend | оценка свободного текста по сценарию ML; карточку с полями — 501 (сравнивает backend) |
| POST | `/api/v1/analyze/grammar` | backend | ошибки грамотности в формате backend (LLM) |
| POST | `/api/v1/recommendations` | backend | до трёх рекомендаций по статистике ошибок (LLM) |
| POST | `/api/v1/generate/correct`, `/analytics/summary`, `/knowledge/index` | backend | пока не реализованы → 501, backend считает сам |

Ответ 501 — нормальная часть контракта: backend (`HybridMLClient`) выполняет такой метод своими
правилами, занятие не останавливается.

## Интеграция с другими частями

```text
АРМ (браузер) ──/ml/incident-types, /ml/dialogue/──> ML
backend ──/api/v1/generate|evaluate|analyze|recommendations──> ML   (501 или сбой → правила backend)
телефония ──/dialogue/turn──> ML ──> реплика ──> TTS ──> телефон рабочего места
ML ──/api/chat──> Ollama (qwen3:4b-instruct)
```

- **Реплики собеседников.** Служба: «<должность> <фамилия>, слушаю вас» → без адреса из карточки
  один раз переспрашивает адрес → «информация принята». Старший группы: доклад → «Понял вас, конец
  связи». Заявитель при перезвоне: «Кто это?», пока не услышит «112 / звонили». Заявитель 112 —
  факты сценария или карточки занятия по ключевым словам вопроса: суть, адрес, пострадавшие, имя.
  Молчание — «Алло?», дважды — отбой.
- **Вызов 112 по карточке занятия.** Если готового сценария нет, собеседник строится из
  `context.card`: содержание карточки подставляет backend, в браузер эталон не попадает.
- **Эталон карточки.** Статус заявителя в эталон не входит: заявитель его не называет, оператор
  определяет его сам.

## Локальная LLM

| Параметр | Значение |
|---|---|
| Модель | `qwen3:4b-instruct` (переменная `LLM_MODEL`) |
| Сервер | Ollama, `OLLAMA_URL` (в стенде `http://ollama:11434`) |
| Скорость | ~3 с на короткий ответ на CPU после прогрева; первый запрос — до 15 с |
| Режим | `think: false`, ответы в JSON (`format: json`) |

Почему instruct-вариант: `qwen3:4b` рассуждает вслух даже с `think: false` — ответ 10+ с и
без готовой фразы.

Реплики в звонках по умолчанию идут по правилам (`DIALOGUE_ENGINE=rules`): это быстро и точно
по регламенту. Свободный диалог через LLM — `DIALOGUE_ENGINE=llm` (модель `DIALOGUE_LLM_MODEL`);
если LLM не ответила за `LLM_TIMEOUT_SEC`, реплика идёт по правилам, звонок не срывается.

## Данные

| Файл | Что это |
|---|---|
| `data/raw/Klassifikator.xlsx` | официальный классификатор происшествий заказчика: 1283 типа, 24 категории, главная служба. Тот же файл при установке стенда загружается в базу backend |
| `data/raw/tickets_32.txt` | примеры обращений для проверки классификации |
| `data/processed/tickets.json` | обращения после разбора (`parse_tickets.py`) |
| `data/processed/classified_tickets.json` | результаты классификации обращений |
| `data/processed/classification_review.json` | разбор качества классификации (`analize_matches.py`) |
| `data/dialogue_scenarios/*.json` | сценарии голосовых вызовов 112: первая фраза, факты с ключевыми словами, условия завершения |

Модель Qwen в репозитории не хранится: её скачивает Ollama (том `ollama-models`).

## Настройки

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `OLLAMA_URL` | `http://ollama:11434` | адрес Ollama |
| `LLM_MODEL` | `qwen3:4b-instruct` | модель для анализа, грамотности, рекомендаций, рассказов заявителей |
| `DIALOGUE_ENGINE` | `rules` | реплики собеседников: `rules` или `llm` |
| `DIALOGUE_LLM_MODEL` | как `LLM_MODEL` | модель для реплик при `llm` |
| `LLM_TIMEOUT_SEC` | `20` | ожидание LLM на реплику; для грамотности и рекомендаций — втрое дольше |
| `LLM_API_URL`, `LLM_API_KEY` | — | вместо Ollama — любой OpenAI-совместимый сервер для реплик |

В стенде переменные задаются в корневом `.env` (шаблон `.env.example` в корне репозитория).

## Ограничения

- Классификация — по признакам и ключевым словам: сложные описания с несколькими событиями
  получают статус `review`, и нужна проверка преподавателем.
- Качество текстов LLM ограничено моделью 4B на CPU: рассказы заявителей и рекомендации стоит
  просматривать при утверждении сценария.
- Коррекция сценария по комментарию преподавателя, аналитика по группе и база знаний пока
  выполняются правилами backend (методы ML отвечают 501).
