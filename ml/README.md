System-112 AI Training Service
Python-сервис для тренажёра операторов системы 112.

Программа:

* анализирует текстовые описания происшествий;
* определяет тип происшествия по официальному классификатору;
* использует локальную нейросеть Qwen для анализа текста;
* создаёт учебные сценарии;
* оценивает ответы оператора по заданным критериям.

Основные компоненты:

classifier.py

Загружает и обрабатывает официальный классификатор Klassifikator.xlsx.

Работает с категориями, группами и типами происшествий.

matcher.py

Сопоставляет описание ситуации с данными классификатора и выбирает наиболее подходящий тип происшествия.

llm_processor.py

Подключает локальную Qwen через Ollama.

Используется для:

* выделения фактов из текста;
* определения неизвестной информации;
* формирования краткого описания ситуации.

Официальная классификация берётся из Klassifikator.xlsx, а не создаётся нейросетью.

scenario_generator.py

Создаёт учебный сценарий на основе типа происшествия.

Поддерживаются уровни сложности:

* easy
* medium
* hard

evaluator.py

Проверяет ответ оператора по критериям сценария.

Определяет:

* выполненные действия;
* пропущенные действия;
* ошибки;
* итоговый балл;
* обратную связь.

api.py

Предоставляет функции программы через REST API на FastAPI.

Метод Endpoint Назначение
GET /health Проверка работы сервиса
POST /classify Классификация ситуации
POST /analyze Анализ текста через Qwen
POST /classify_with_llm Анализ текста и классификация
POST /generate_scenario Генерация учебного сценария
POST /evaluate Оценка ответа оператора

После запуска API автоматически доступна документация Swagger:

http://127.0.0.1:8000/docs

main.py

Тестовый файл для проверки классификатора, генерации сценариев и оценки ответов.

parse_tickets.py

Обрабатывает исходные обращения из набора данных.

analyze_matches.py

Используется для анализа результатов классификации.

В программе используются данные, предоставленные руководством проекта:
data/raw/Klassifikator.xlsx

Официальный классификатор происшествий.

data/raw/tickets_32.txt

Набор примеров обращений.

Обработанные данные:
data/processed/

Содержат результаты обработки обращений и классификации.

Локальная нейросеть
Для анализа текста используется Qwen через Ollama.
Модель:
qwen3:4b

Ollama и модель устанавливаются отдельно и не хранятся в GitHub.

Требования

* Python 3.12
* Ollama
* Qwen qwen3:4b

Python-зависимости указаны в:
requirements.txt

Установка

Создать виртуальное окружение:
python -m venv .venv

Активировать его.

Windows:
.venv\Scripts\activate

Linux/macOS:
source .venv/bin/activate

Установить зависимости:
pip install -r requirements.txt

Установить Ollama и загрузить модель:
ollama pull qwen3:4b

Запустить сервис:
uvicorn api:app --reload --host 127.0.0.1 --port 8000

После запуска API доступен по адресу:
http://localhost:8000/docs

В репозитории предоставлены файлы для контейнеризации сервиса:

- `Dockerfile` — образ FastAPI-приложения
- `docker-compose.yml` — совместный запуск API и Ollama
- `.dockerignore` — исключения при сборке образа
- `.env.example` — шаблон переменных окружения

Схема запуска:

    docker compose up --build

API внутри контура будет доступен по адресу:

    http://localhost:8000/docs

Для локальной разработки Docker не обязателен — сервис запускается
напрямую через `uvicorn api:app --reload`.

Основные файлы данных:

data/raw/Klassifikator.xlsx
data/raw/tickets_32.txt
data/processed/tickets.json
data/processed/classified_tickets.json
data/processed/classification_review.json

Сама модель Qwen также не загружается в репозиторий и устанавливается отдельно через Ollama.

Интеграция с телефонией и Backend

Модуль integration/ подключается в api.py одной строкой и реализует контракты из ТЗ (§6):

* POST /dialogue/turn — реплики виртуальных собеседников в звонках (контракт telephony/API.md §3):
  правила по типу звонка или локальная LLM (DIALOGUE_ENGINE=llm, модель DIALOGUE_LLM_MODEL);
  сценарии голосовых вызовов 112 — data/dialogue_scenarios/;
* POST /api/v1/generate/scenarios — генерация сценариев для Backend по классификатору (generate_scenario)
  с полным эталоном карточки: тип ЕКП, реальный адрес Москвы, ФИО и АОН заявителя, пострадавшие,
  рассказ заявителя от первого лица (пишет LLM, без неё — шаблон);
* POST /api/v1/evaluate/attempt — оценка свободного текстового ответа по сценарию ML (evaluate_answer);
  карточку АРМ-112 с полями оценивает Backend (501);
* POST /api/v1/analyze/grammar, POST /api/v1/recommendations — грамотность текста и рекомендации (LLM);
* GET /incident-types?q= — поиск по классификатору для поля «Что случилось?» в АРМ;
* остальные методы контракта Backend (backend/docs/INTEGRATION.md §1) отвечают 501 —
  Backend считает их своими правилами, пока они не реализованы здесь.

Модель по умолчанию — qwen3:4b-instruct (переменная LLM_MODEL): без рассуждений вслух, ~3 с на ответ на CPU.

В полном стенде (корневой docker-compose.yml) сервис доступен как http://ml:8000,
Ollama — http://ollama:11434 (профиль llm).
